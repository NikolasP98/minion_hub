## 1. An unusable configured rate leaves no `pos_emissions` row (spec ⚠️ A2)

- **Site:** `src/server/services/pos-emission.service.ts`, `triggerShadowEmission`
  (the `resolveIgvRate(finSettings)` call).
- **What:** `resolveIgvRate` throws `PosError('invalid_tax_rate')` for a rate
  SUNAT cannot accept (non-finite, outside `(0, 1)`, or exactly `0`). That throw
  happens *before* the serie allocation and the `pos_emissions` insert, so the
  failure is only `console.error`-logged. Every *other* shadow-emission failure
  degrades an existing row to `status='error'`, which the ticket-detail endpoint
  surfaces.
- **Verified (S2):** checkout is never blocked — `triggerShadowEmission`
  resolves, the cashier's request is untouched. Covered by the test "an unusable
  configured rate never blocks checkout and emits nothing". So the spec's A2
  claim holds for the part that matters (no propagation to the cashier) and does
  *not* hold for the "surfaces as a `status='error'` row" part.
- **Why not fixed here:** making it visible needs either (a) an insert of a
  rate-independent `pos_emissions` row before the rate is resolved, or (b) an
  error row with no serie/correlativo. (a) burns a SUNAT correlativo on a
  document that is never built; (b) needs the columns to be nullable, i.e. DDL,
  which this spec forbids (§5 "Zero DDL"). Both are design calls beyond a
  three-slice fix.
- **Suggested fix:** treat "org misconfiguration" as its own observable state —
  e.g. a `pos_emissions.status = 'config_error'` row with a null serie (one
  additive migration), or surface it on the POS settings page as a validation
  error at *save* time so it can never reach emission.

## 2. Exonerado / inafecta document shapes are still unsupported (spec ⚠️ A2, §5)

- **Site:** `src/server/finance/tax.ts` (`resolveIgvRate`'s doc-comment) — the
  `rate <= 0` branch.
- **What:** an org that sets `tax_rate = 0` gets a hard `invalid_tax_rate` at
  emission time. A zero-rated operation is a different UBL document (SUNAT's
  9997/9998 tax-category family, different `LegalMonetaryTotal` buckets), not a
  0% version of a gravada one, so refusing is correct — but the org's real need
  (emitting exonerated/inafecta documents) is unmet and unrepresented in the
  data model.
- **Why not fixed here:** explicitly out of scope (§5); it is a feature spec, not
  a rate fix. Per-line/per-product affectation types belong to the same future
  work.

## 3. Deviations from the spec's machine-checkable DoD (recorded, not fixed)

1. **`rg -n '0\.18|DEFAULT_IGV_RATE' src/server/ | grep -v -E 'finance/tax\.ts|finance\.service\.ts|\.test\.ts'`
   returns exactly one hit** — `src/server/db/pg-finance-schema.ts:243`, the
   pre-existing `tax_rate numeric not null default '0.18'` column default (it
   mirrors `supabase/migrations/20260708180000_fin_settings.sql`). Changing a
   column default requires a migration, which §5 forbids. It is a DB default,
   not a rate constant in emission logic. The spec's grep did not anticipate it.
2. **`bun run check` does not type-check `scripts/`** — `.svelte-kit/tsconfig.json`
   includes only `src/`, `test/`, `tests/` and the vite config. So spec
   assumption 5 ("any required new field breaks them at compile time") is true
   only under a separate tsconfig. The three beta scripts plus
   `scripts/_emission-rate-arg.ts` were type-checked with an ad-hoc tsconfig
   including `scripts/**/*.ts`: zero errors in those four files (the rest of
   `scripts/` has pre-existing errors — missing `bun`/`bun:sqlite` types and
   several implicit `any`s — unrelated to this work and left alone).
3. **The live SUNAT beta re-verification (§6 step 3 / S3 "Live beta
   re-verification") was NOT run.** It needs `.beta-cert/` (generated by
   `scripts/gen-beta-cert.sh`) and outbound network access to SUNAT's beta
   endpoint, neither of which exists in this environment. The four CDR
   descriptions the spec's ship gate asks for (18% and 10% invoice + resumen)
   are therefore still owed before the ship gate can be signed off. The unit
   suite proves internal totals consistency at 4 rates × 4 line-sets exactly,
   which is the invariant SUNAT's "totales no consistentes" check enforces — but
   it is not the same as SUNAT's own `ResponseCode 0`.
4. **§6 step 4 (dev-org shadow-mode ticket) and step 5 (byte-equal document for
   a null-rate org, live) were not run** — no dev DB/org in this environment.
   Step 5's assertion is covered as a unit test instead (`tax.test.ts` → "the
   fallback reproduces the pre-change document byte for byte", against the
   golden fixture captured from `a3b57e2`).
