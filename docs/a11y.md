# Accessibility gates

One command checks every accessibility gate the Hub has. Run it after any UI change.
**Baselines only decrease.**

```bash
bun run a11y                    # suppressions, patterns, specs, stories (no backend needed, ~6 min)
bun run a11y --all              # + pages: runs the page sweep, needs the QA stack (`bun run qa:up`)
bun run a11y --only stories --stories Dropdown    # one story file while you iterate
bun run a11y --only pages --routes /crm,/pos/sell # a route subset
bun run a11y --only pages --artifacts <dir>       # judge run-sweep--*.json from a CI artifact, no stack
bun run a11y --update-baseline  # after a fix: ratchet the baselines DOWN and commit them
```

CI runs the same command: the `a11y` job runs `bun run a11y --ci`, and the `qa-stack` job
runs `bun run a11y --only pages --ci`. `--ci` only changes one thing: a count that fell
does not fail (CI cannot commit a ratchet). Locally a fallen count fails until you run
`--update-baseline` and commit the result.

## Gates

| Gate           | What fails it                                                                                                            | Baseline                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `suppressions` | A changed file gains a `svelte-ignore a11y_*` rule token, or the total rises                                             | `scripts/.design-lint-baseline.json` → `a11y-ignore` |
| `patterns`     | Any failing test in a `*.test.ts` file that uses `assertPattern`                                                         | none (must pass)                                     |
| `specs`        | `canvas-accessibility.spec.ts`, `workshop-accessibility.spec.ts` or `aria-snapshots.spec.ts` fails (Chromium)            | `tests/e2e/ui-audit/aria-snapshots/` (aria only)     |
| `stories`      | A story's axe violation count for a rule rises, a new story has any violation, or a story that ran stops running         | `tests/ui-audit/a11y-ledger.json` → `stories`        |
| `pages`        | The same, per page × viewport, measured by the page sweep after the page settled. Also fails when the sweep itself fails | `tests/ui-audit/a11y-ledger.json` → `pages`          |

Rules checked by `stories` and `pages`: axe-core rules tagged WCAG 2.0, 2.1 or 2.2, level A
or AA (`tests/ui-audit/a11y-tags.json`). A count is the number of elements breaking the rule.

The ledger is sparse: a page or story that is not in it has a baseline of zero, so new
pages and stories must be clean. `"unmeasured"` marks a story or page that could not be
checked when the baseline was taken (its test fails, or the page never settled); a
measured row may not become unmeasured. `pageScenarios` lists the viewports the ledger
gates; rows from other viewports are reported as `ungated`.

Stories are measured with the app's real styles: the story test lane runs the same CSS
producer (Tailwind) as the app and the built Storybook, so the page has its theme background.
The story `Foundations/Rendering contract` fails when that producer is missing. The story
baseline was re-measured once under real rendering on 2026-11-27 (749 → 1095 violations: 255
rows up by 525, 61 rows down by 179): before that the lane measured every story on a white
page, so dark-theme failures passed and correct light-on-dark text failed. That was a
re-measurement, not a regression; from there the baseline only decreases again.

Never raise a baseline by hand. If a count rose, fix the markup.

## `assertPattern`: prove a widget in one call

axe cannot see keyboard behavior. `assertPattern` (`$lib/a11y/assert-pattern`) checks a
widget against its [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/)
pattern: roles, accessible names, states, exactly one tab stop, the keys the pattern
requires, and that focus never lands on the document body or on hidden content. It throws
one error that lists every broken expectation:

```
assertPattern(listbox): 2 problem(s)
  - [one-tab-stop] exactly one tab stop in the listbox (roving tabindex or aria-activedescendant); found 2: div[role=option]"A", div[role=option]"B" — got div[role=listbox]
  - [key-end] End moves to the last item — got div[role=option]"A"
```

It is plain DOM code, so the same call works in a mounted unit test (happy-dom) and in a
story `play` function (real Chromium). Name the test file `*.mounted.test.ts`; the
`patterns` gate picks up every `*.test.ts` that uses it.

```ts
// @vitest-environment happy-dom
import { render } from '@testing-library/svelte';
import { assertPattern } from '$lib/a11y/assert-pattern';

it('is a conforming listbox', async () => {
  const { container } = render(MyListbox, { options });
  await assertPattern(container, 'listbox');
});
```

The first argument is the widget or any ancestor of it. Pass `document.body` when the
widget portals out of its container.

### One example per pattern

```ts
// listbox: options are role="option" with aria-selected; Up/Down, Home, End.
await assertPattern(container, 'listbox');
await assertPattern(container, 'listbox', { orientation: 'horizontal', typeahead: true });

// menu: items are menuitem/menuitemcheckbox/menuitemradio. With an opener it must also
// close on Escape and return focus to that opener.
await user.click(trigger);
await assertPattern(document.body, 'menu', { opener: trigger });

// tabs: one selected tab that controls a labelled tabpanel; Left/Right wrap, Home, End.
await assertPattern(container, 'tabs');
await assertPattern(container, 'tabs', { orientation: 'vertical' });

// dialog: named, modal, focus starts inside, Escape closes and returns focus to the opener.
await user.click(openButton);
await assertPattern(document.body, 'dialog', { opener: openButton });

// alertdialog: a dialog that must also point aria-describedby at its message.
await user.click(deleteButton);
await assertPattern(document.body, 'alertdialog', { opener: deleteButton });

// combobox: aria-expanded, ArrowDown opens the popup named by aria-controls, focus stays
// on the input while aria-activedescendant moves, Escape closes.
await assertPattern(container, 'combobox');

// grid: ONE tab stop for the whole grid; arrows between cells, Home/End in the row,
// Ctrl+Home / Ctrl+End across the grid.
await assertPattern(container, 'grid');
```

### Options

| Option        | Use                                                                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `orientation` | `'vertical'` or `'horizontal'` arrow axis for listbox, menu and tabs. Default: vertical, tabs horizontal                                             |
| `opener`      | The control that opened a dialog or popup menu. Required for dialogs: without it focus return cannot be checked and `focus-return` is reported       |
| `typeahead`   | Also check that typing a letter moves to the item starting with it (listbox, menu)                                                                   |
| `skip`        | Rule ids to waive, for example `skip: ['key-wrap']`. A waiver is visible in the test; add a comment saying why                                       |
| `press`       | Key driver. The default dispatches synthetic `keydown`/`keyup`, which does not trigger native behavior such as a native `<dialog>` closing on Escape |

In a story `play` function, drive real key handling through `press`:

```ts
import { userEvent } from 'storybook/test';
await assertPattern(canvasElement, 'tabs', { press: (key) => userEvent.keyboard(`{${key}}`) });
```

`checkPattern(root, pattern, options)` returns the problems as data
(`{ rule, expected, element }[]`) instead of throwing. `PATTERN_RULES` lists the rule ids
of each pattern. The helper waits a frame after every key, so do not run it under fake timers.

Limits: Tab-key focus trapping in dialogs, right-to-left arrow keys, and screen-reader
output are not checked.
